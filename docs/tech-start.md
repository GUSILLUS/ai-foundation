# AI Foundation — технічний старт

Nov 8, 2026 · @Ivan Ivakhnenko

## Призначення

Цей документ відповідає на питання «як саме починаємо»: рішення до першого рядка коду, структура репозиторію, середовище розробки, перевірки й критерій готовності першого етапу. Бачення («що і навіщо») — в окремому документі `docs/vision.md`, короткий постійний контекст для агента — у `CLAUDE.md`.

Після створення репозиторію головним джерелом правди стає репо: зміни рішень фіксуються в `docs/decisions/`, а не тут.

## Структура репозиторію

Репозиторій плагінів містить лише код, шаблони й документацію системи; клієнтські дані живуть окремо.

```
ai-foundation/
├── .claude-plugin/
│   └── marketplace.json        # каталог плагінів для встановлення
├── plugins/
│   ├── af-core/                # контекст, init, шаблони, робочий ланцюг
│   │   ├── .claude-plugin/plugin.json
│   │   ├── skills/<скіл>/SKILL.md (+ assets/, references/)
│   │   ├── commands/
│   │   ├── hooks/
│   │   └── tests/
│   ├── af-controls/            # бар’єри безпеки, бібліотека хуків
│   ├── af-handoff/
│   └── af-metrics/
├── shared/                     # канонічні джерела спільного коду
├── scripts/
│   ├── validate.ts             # одна команда перевірки
│   └── sync-shared.ts          # синхронізація копій, режим --check
├── docs/
│   ├── vision.md
│   ├── tech-start.md
│   └── decisions/              # ADR: одне рішення — один файл
├── CLAUDE.md                   # постійний контекст для агента
├── CHANGELOG.md
├── LICENSE                     # MIT
└── package.json

~/ai-foundation-data/           # поза репозиторієм плагінів
└── projects/<проєкт>/          # context.md, specs, plans, handoff
```

Точні шляхи маніфестів і папок звіряємо з документацією Claude Code (див. останній розділ).

## Середовище розробки

Плагіни розробляються на локальній копії репозиторію, а Claude Code підхоплює їх без перевстановлення після кожної зміни.

- **Інструменти:** Node ≥ 22.18 (запускає `.ts` напряму), git, Claude Code ≥ 2.1.321.
- **Локальне підключення:** Claude Code завантажує плагін з локальної папки або локальний маркетплейс; точний спосіб (прапорець запуску чи команда додавання маркетплейсу) звіряємо з документацією.
- **Пісочниця:** окремий тестовий проєкт без клієнтських даних для ручної перевірки хуків і скілів.
- **Робочі копії:** доки плагіни нестабільні, клієнтські проєкти працюють на останній стабільній версії з маркетплейсу, а не на локальній копії.

## Команда перевірки та CI

Одна команда `npm run validate` запускає все, і та сама команда працює в CI на кожен push.

| Перевірка | Що ловить |
| --- | --- |
| Маніфести | Неправильний JSON, відсутні поля, невідповідність назви плагіна й папки, версія не в форматі semver |
| Скіли | Frontmatter (name, description), ліміт довжини опису, посилання на неіснуючі файли в `assets/` і `references/` |
| Хуки | Синтаксис і типи (`tsc --noEmit`), реєстрація кожного хука в конфігурації плагіна |
| Спільний код | `sync-shared --check`: копії в плагінах збігаються з канонічними джерелами |
| Тести | `node --test` для хуків на фікстурах |
| Секрети | Жодних токенів, ключів чи `.env` у репозиторії |
| Залежності між плагінами | Посилання за іменем, мінімальна версія вказана й існує |

CI — GitHub Actions з матрицею `ubuntu-latest` + `windows-latest` і Node 22 + 24; Claude Code — закріплена версія з `package.json`. Окремий не блокуючий job раз на тиждень перевіряє `@latest`. macOS додаємо, коли з’являться залежні від ОС частини (наприклад, сховище ключів).

## Як тестуємо хуки й скіли

Хуки тестуються детерміновано на фікстурах, скіли — сценаріями, а реальне використання скілів міряється окремо, бо пройдений тест не означає, що агент викликає скіл.

- **Хуки.** Кожен хук отримує JSON на вхід і повертає рішення. Тест подає записаний вхід (фікстуру) і перевіряє вихід і код завершення. Обов’язкові випадки: звичайний шлях, блокування, зламаний або порожній вхід (хук деградує, а не падає).
- **Скіли.** Для кожного скіла — кілька сценаріїв: запит, очікувана поведінка (скіл викликано, гейт спрацював, артефакт створено). Запускаються вручну в пісочниці; результат фіксується в журналі.
- **Обходи.** Окремий облік: скільки разів скіл мав спрацювати і скільки спрацював. Це дані для метрик, а не тест.
- **Регресія сетапу.** Набір тестових задач з відомим добрим результатом; проганяється після змін у скілах, ролях чи інструкціях.
