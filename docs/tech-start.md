# AI Foundation — технічний старт

Nov 8, 2026 · @Ivan Ivakhnenko · оновлено 21.11.2026 після завершення етапу 1

## Призначення

Цей документ відповідає на питання «як саме починаємо»: рішення до першого рядка коду, структура репозиторію, середовище розробки, перевірки й критерій готовності першого етапу. Бачення («що і навіщо») — в окремому документі `docs/vision.md`, короткий постійний контекст для агента — у `CLAUDE.md`.

Після створення репозиторію головним джерелом правди стає репо: зміни рішень фіксуються в `docs/decisions/`, а не тут.

## Рішення до першого рядка коду

Ці рішення найдорожче переробляти після старту. Усі рішення прийняті; зміна будь-якого з них — новим ADR у `docs/decisions/`.

## Структура репозиторію

Репозиторій плагінів містить лише код, шаблони й документацію системи; клієнтські дані живуть окремо.

```
ai-foundation/
├── .claude-plugin/
│   └── marketplace.json        # каталог плагінів (маркетплейс ai-foundation)
├── .github/workflows/ci.yml    # validate на Ubuntu і Windows, Node 22.18 і 24
├── plugins/
│   ├── af-core/                # контекст, init, шаблони, робочий ланцюг (поки порожній)
│   ├── af-controls/            # бар’єри безпеки
│   │   ├── .claude-plugin/plugin.json
│   │   ├── hooks/hooks.json    # реєстрація хуків (exec-форма)
│   │   ├── hooks/env-guard.ts  # точки входу хуків
│   │   ├── lib/env-guard.ts    # логіка, яку тестуємо
│   │   ├── lib/shared/         # копії з shared/ (npm run sync), не редагувати
│   │   └── tests/              # тести й синтетичні фікстури
│   ├── af-handoff/             # передача стану між сесіями (поки порожній)
│   └── af-metrics/             # аналізатор історії сесій
│       ├── scripts/analyze-history.ts
│       ├── lib/                # transcripts, inventory, metrics, report
│       └── tests/
├── shared/                     # канонічні джерела спільного коду + sync.json (мапа копій)
├── scripts/
│   ├── validate.ts             # npm run validate
│   ├── checks/                 # окремі перевірки validate
│   ├── sync-shared.ts          # npm run sync / --check
│   ├── test.ts                 # npm test
│   ├── lib/                    # спільні утиліти скриптів
│   └── tests/                  # тести валідатора й синхронізації
├── docs/
│   ├── vision.md
│   ├── tech-start.md
│   ├── install-check.md        # перевірка встановлення з маркетплейсу + журнал
│   ├── ai-foundation-handoff.md # стислий перенос контексту проєкту
│   └── decisions/              # ADR: одне рішення — один файл
├── CLAUDE.md                   # постійний контекст для агента
├── CHANGELOG.md
├── LICENSE                     # MIT
├── package.json                # engines, config.claudeCodeVersion, скрипти
└── tsconfig.json               # erasableSyntaxOnly, verbatimModuleSyntax

~/ai-foundation-data/           # поза будь-яким git, на кожній машині
├── projects/<проєкт>/          # context.md, specs, plans, handoff (з етапу 2)
└── metrics/                    # inventory-<дата>.json, baseline-<дата>.md/.json
```

Структуру звірено з документацією Claude Code (ADR 0001) і реалізовано в етапі 1.

## Середовище розробки

Плагіни розробляються на локальній копії репозиторію, а Claude Code підхоплює їх без перевстановлення після кожної зміни.

- **Інструменти:** Node ≥ 22.18 (запускає `.ts` напряму), git, Claude Code ≥ 2.1.321.
- **Локальне підключення:** `claude --plugin-dir ./plugins` вантажить усі плагіни репозиторію на одну сесію; після змін у хуках чи агентах — `/reload-plugins`.
- **Пісочниця:** окремий тестовий проєкт без клієнтських даних для ручної перевірки хуків і скілів.
- **Робочі копії:** клієнтські проєкти працюють на версії з git-маркетплейсу (`claude plugin marketplace add GUSILLUS/ai-foundation`), а не на локальній копії: маркетплейс з локальної папки вантажить робочі файли на місці й ігнорує версії. Процедура перевірки встановлення — `docs/install-check.md`.

## Команда перевірки та CI

Одна команда `npm run validate` запускає все, і та сама команда працює в CI на кожен push.

| Перевірка (`id`) | Що ловить |
| --- | --- |
| Маніфести (`manifests`) | Невалідний JSON, semver, ім’я = папка, префікс `af-`, записи маркетплейсу ↔ папки, версія лише в `plugin.json`, прямі слеші, залежності за іменем з мінімальною версією, що існує; `af-core` і `af-controls` без залежностей |
| Скіли (`skills`) | Frontmatter, `description` + `when_to_use` ≤ 1 536 символів, `SKILL.md` ≤ 500 рядків. Посилання на неіснуючі файли в `assets/` і `references/` — додати разом з першим скілом |
| Хуки (`hooks`) | Лише exec-форма (`node` + `args`), явний `timeout` ≤ 60 с, файл хука існує всередині плагіна |
| Claude Code (`claude`) | `claude plugin validate --strict` для маркетплейсу й кожного плагіна; версія CLI не нижча за закріплену |
| Типи (`typecheck`) | `tsc --noEmit`, зокрема заборона нестираного синтаксису |
| Спільний код (`sync`) | Копії збігаються з `shared/`; немає відсутніх і зайвих копій |
| Секрети (`secrets`) | Токени, ключі, `.env`; у звіті лише файл, рядок і тип |
| Фікстури (`fixtures`) | Лише синтетичні дані: білий список значень, без e-mail, реальних шляхів і вільного тексту |
| Тести (`tests`) | `node --test` для скриптів і плагінів |

CI — GitHub Actions з матрицею `ubuntu-latest` + `windows-latest` і Node 22 + 24; Claude Code — закріплена версія з `package.json`. Окремий не блокуючий job раз на тиждень перевіряє `@latest`. macOS додаємо, коли з’являться залежні від ОС частини (наприклад, сховище ключів).

## Як тестуємо хуки й скіли

Хуки тестуються детерміновано на фікстурах, скіли — сценаріями, а реальне використання скілів міряється окремо, бо пройдений тест не означає, що агент викликає скіл.

- **Хуки.** Кожен хук отримує JSON на вхід і повертає рішення. Тест подає записаний вхід (фікстуру) і перевіряє вихід і код завершення. Обов’язкові випадки: звичайний шлях, блокування, зламаний або порожній вхід (хук деградує, а не падає).
- **Скіли.** Для кожного скіла — сценарії у форматі вбудованого `claude plugin eval` (`evals/` у плагіні): запит, грейдер `tool_used: Skill` (скіл справді викликано) і грейдер результату; порівняння з прогоном без плагіна. Прогони коштують токенів, тож запускаються свідомо, не на кожен push.
- **Обходи.** Скільки разів скіл викликали насправді — з аналізатора історії (`af-metrics`), далі з OTel (`skill.name`) і `/usage`. Базова лінія етапу 1: 31 виклик скілів на 560 промптів.
- **Регресія сетапу.** Набір тестових задач з відомим добрим результатом; проганяється після змін у скілах, ролях чи інструкціях.
