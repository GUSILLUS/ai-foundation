# 0002 — Базова лінія метрик з історії сесій

- **Статус:** Прийняте (2026-11-20)
- **Дата:** 2026-11-20
- **Пов’язано:** ADR 0001 (пункт 11 «Транскрипти», «Наслідки» п. 9), `docs/tech-start.md` — останній пункт етапу 1

## Контекст

Принцип 4: спершу виміряй, потім покращуй. Перш ніж додавати скіли, ролі чи самопокращення, потрібна базова лінія: як я зараз працюю з Claude Code. Джерело — транскрипти, які Claude Code уже зберігає локально (`<CLAUDE_CONFIG_DIR>/projects/<project>/<session>.jsonl`, за замовчуванням `~/.claude`).

Обмеження з ADR 0001:

- формат записів **внутрішній і змінюється між версіями** — парсер має бути толерантним;
- токени дублюються: одна відповідь моделі — кілька рядків з однаковим `message.id`;
- транскрипти містять вміст файлів, вхідні дані інструментів, e-mail — читаємо лише дозволені поля;
- історія CLI живе 30 днів (`cleanupPeriodDays`), тож базова лінія покриває лише те, що лишилося.

Далі, після базової лінії, поточні метрики збирає вбудована телеметрія (OTel), а аналізатор лишається інструментом для історії.

## Рішення

### 1. Що аналізуємо

- Усі `*.jsonl` під `<CLAUDE_CONFIG_DIR>/projects/`, включно з транскриптами субагентів, якщо вони лежать там окремими файлами.
- **Дедуплікація глобально, а не в межах файлу:** `/branch`, `--fork-session` і resume копіюють історію в новий файл. Ключі: `message.id` для відповідей моделі, `uuid` для решти записів, `id` для викликів інструментів.
- Записи без потрібних полів пропускаємо й рахуємо як «нерозпізнані» за типом — це сигнал, що формат змінився.

### 2. Перший прогін — інвентаризація

Режим `--inventory` нічого не рахує, а лише описує дані агрегатами:

- кількість файлів і рядків, діапазон дат;
- типи записів, значення `entrypoint`, версії Claude Code;
- набір ключів (без значень) для кожного типу запису.

Інвентаризація на Windows-машині закриває відкриті питання 4 і 5 з ADR 0001: чи збігається схема і чи потрапляють туди сесії Desktop. Лише після неї фіксуємо остаточний парсер.

### 3. Визначення метрик

| Метрика | Визначення | Поля |
| --- | --- | --- |
| **Сесія** | Унікальний `sessionId`. Тривалість — від першого до останнього `timestamp`; простої понад 30 хв не рахуються в «активний час» | `sessionId`, `timestamp`, `entrypoint`, `version` |
| **Промпт людини** | Запис `user` поза субагентом (`isSidechain: false`), вміст якого не є результатом інструмента, без службових позначок (мета-повідомлення, підсумок стиснення) | `type`, `isSidechain`, тип блоків `message.content` (без тексту) |
| **Відповідь моделі** | Унікальний `message.id` запису `assistant` | `message.id`, `message.model` |
| **Токени** | Сума `usage` по унікальних `message.id`: input, output, cache read, cache creation, thinking — окремо для кожної моделі | `message.usage.*` |
| **Вартість** | Останній знімок `cost-state.totalCostUSD` у сесії. Якщо знімка немає (старі версії), вартість — «невідома»; власну таблицю цін не ведемо (принцип 7) | `cost-state` |
| **Виклики інструментів** | Блоки `tool_use` за назвою; MCP — згруповані за сервером (`mcp__<сервер>__*`) | `name` |
| **Скіли й субагенти** | Для інструмента `Skill` — назва скіла; для `Agent`/`Task` — тип субагента. Це єдині поля з `input`, які читаємо | `input.skill`, `input.subagent_type` |
| **Помилки** | (а) результат інструмента з `is_error: true` — за назвою інструмента; (б) помилки хуків з `hookErrors`; (в) записи помилок API, якщо інвентаризація їх знайде | `is_error`, `hookErrors` (кількість), підтип `system` |
| **Відхилені дії** | `permissionDecision.decision` ≠ `accept`, за джерелом (`user_reject`, `hook`, `config` …). Точний набір значень уточнює інвентаризація | `permissionDecision.decision`, `.source` |
| **Стиснення контексту** | Кількість стиснень у сесії (ручних і автоматичних) | службові записи стиснення |

### 4. Наближена оцінка раундів правок

Прямої метрики «скільки разів я виправляв агента» немає. Пропоную три наближення, які разом дають картину:

1. **Хід із правками** — хід (від промпту людини до наступного), у якому був хоч один успішний `Edit`/`Write`/`MultiEdit`/`NotebookEdit`.
2. **Раунд правок** — хід із правками, за яким іде ще один хід із правками в тій самій сесії. Рахуємо, скільки разів поспіль агент знову береться змінювати код після мого наступного промпту.
3. **Повторно змінені файли** — файли, змінені в ≥ 2 різних ходах однієї сесії. Шлях файлу читаємо лише в пам’яті як ключ і **ніколи не виводимо** — у результат іде тільки кількість.

Головне число — частка ходів із правками, після яких одразу йде ще один хід із правками. Це оцінка, а не факт: наступний хід може бути й новою задачею. Звіт так її й підписує.

### 5. Результат

- Файл `~/ai-foundation-data/metrics/baseline-<дата>.json` і короткий `baseline-<дата>.md` для читання.
- Розрізи: загалом, по тижнях, по проєктах, по `entrypoint`, по моделях, по версіях Claude Code.
- **Лише агрегати:** лічильники, суми токенів, назви інструментів, скілів, субагентів і моделей, версії, дати. Жодних текстів промптів і відповідей, шляхів файлів, команд, вмісту інструментів.
- **Назви проєктів.** Це назви робочих папок (часто — назви клієнтів). Файл лишається локально поза git, тож за замовчуванням пропоную справжні назви. Прапорець `--anonymize` замінює їх на стабільні псевдоніми (`project-1`, …) — для випадків, коли звітом треба поділитися.

### 6. Реалізація

- `plugins/af-metrics/scripts/analyze-history.ts` — TypeScript без залежностей, потокове читання рядків (транскрипти бувають великими), лише читання транскриптів.
- Запуск: `npm run metrics:baseline` з репозиторію або `node <шлях>/analyze-history.ts` з установленої копії. Прапорці: `--inventory`, `--since <дата>`, `--config-dir`, `--out`, `--anonymize`.
- Команду чи скіл для сесії не робимо — на етапі 1 це функціональність (CLAUDE.md, «Поточний етап»).
- Парсер читає поля через білий список; невідомі типи записів і поля ігнорує, але рахує в інвентаризації.
- Тести — лише на синтетичних фікстурах. Разом з аналізатором до `validate` додається перевірка фікстур за білим списком (ADR 0001, «Наслідки» п. 9). Префікс дозволених шляхів у фікстурах — `/fixtures/` і `C:/fixtures/` (для перевірки Windows-шляхів).

## Наслідки

- Базова лінія — знімок наявної історії. Через 30-денне зберігання вона неповна; що раніше піднятий `cleanupPeriodDays`, то більше даних матиме наступний прогін.
- Кожне оновлення Claude Code може змінити формат. Захист: інвентаризація показує «нерозпізнані» записи, а фікстури позначені версією, з якої знято структуру.
- Оцінка раундів правок навмисно груба. Якщо вона виявиться марною, її можна прибрати без зміни решти (принцип 7).

## Ухвалено при затвердженні

1. Визначення раунду правок (п. 4) прийняте як перше наближення.
2. Назви проєктів у звіті — справжні за замовчуванням; `--anonymize` — коли звітом треба поділитися. Звіт інвентаризації назв проєктів не містить зовсім: його можна пересилати для аналізу схеми.
3. Сесії Desktop і Cowork включаються в базову лінію, якщо інвентаризація їх знайде; розріз по `entrypoint` показує їх окремо.
