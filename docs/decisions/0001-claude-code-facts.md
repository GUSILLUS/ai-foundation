## Деталі за пунктами

### 1. Формат і шляхи маніфестів ⚠️

**Підтвердилось:**

- Маркетплейс — `.claude-plugin/marketplace.json` у корені репозиторію. Корінь маркетплейсу — папка, що містить `.claude-plugin/`; від неї розв’язуються відносні шляхи.
- Маніфест плагіна — `<плагін>/.claude-plugin/plugin.json`. Усе інше (`skills/`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`) лежить у корені плагіна, **не** в `.claude-plugin/` — компоненти звідти не вантажаться.
- Структура з `docs/tech-start.md` відповідає документації.

**Обов’язкові поля:**

- `marketplace.json`: `name`, `owner` (з обов’язковим `owner.name`), `plugins`. Запис плагіна: `name` і `source`.
- Відносний `source` має починатися з `./` (наприклад, `"./plugins/af-core"`), без `..` і без зворотних слешів. Альтернатива — `metadata.pluginRoot: "./plugins"` і голі імена (`"source": "af-core"`), з v2.1.239.
- `plugin.json`: **лише `name`** (kebab-case). Сам маніфест необов’язковий: без нього ім’я береться із запису маркетплейсу чи назви папки.

**Відрізняється від припущень:**

- Claude Code **не перевіряє `version` на semver** — це рядок. Перевірку semver робить наш `validate`.
- Невідомий ключ верхнього рівня мовчки відкидається (опечатка не ламає завантаження). `claude plugin validate` показує це як попередження, `--strict` — як помилку.
- `version` не можна задавати і в `plugin.json`, і в записі маркетплейсу: переможе `plugin.json`, а `validate` попередить про розбіжність. Якщо `version` задано, користувачі не отримують нових комітів, доки рядок не зміниться. Це збігається з нашим semver-підходом, але робить підняття версії обов’язковим кроком релізу.
- **Файли поза папкою плагіна не копіюються в кеш.** Скрипт, що читає `../shared`, після встановлення з маркетплейсу їх не знайде. Шлях компонента, що виходить за корінь плагіна, відхиляється (`path escapes plugin directory`). Симлінки в межах маркетплейсу розгортаються при копіюванні, але для маркетплейсу з локальної папки зберігаються лише симлінки всередині плагіна, а на Windows симлінки потребують Developer Mode. **Висновок: наше рішення «канонічний файл + копії + `sync --check`» — правильне; симлінки не беремо.**
- `CLAUDE.md` у корені плагіна **не вантажиться** як контекст (`validate` про це попереджає). Інструкції в плагіні — лише через скіли.
- Папка `bin/` на верхньому рівні плагіна додається в `PATH`, але claude.ai і Cowork відмовляються встановлювати плагін, що її має. Виконувані скрипти — у `scripts/` чи `hooks/`, виклик через `${CLAUDE_PLUGIN_ROOT}/...`.
- Змінні шляхів: `${CLAUDE_PLUGIN_ROOT}` (змінюється з кожною версією — стан там не зберігати), `${CLAUDE_PLUGIN_DATA}` (`~/.claude/plugins/data/<id>/`, переживає оновлення, видаляється при деінсталяції), `${CLAUDE_PROJECT_DIR}`.

### 2. Локальне підключення для розробки ✅

- `claude --plugin-dir <шлях>` вантажить плагін на одну сесію без встановлення (id `<name>@inline`). Прапорець повторюваний.
- З v2.1.265 `--plugin-dir ./plugins` вантажить **кожну підпапку з `.claude-plugin/plugin.json`** — тобто всі чотири `af-*` однією командою. Передавати корінь репозиторію не можна: `--plugin-dir` не читає `marketplace.json`, і плагіни з `plugins/` не завантажаться без жодної помилки.
- Після змін на диску — `/reload-plugins` у сесії. Зміни лише в тексті `SKILL.md` підхоплюються автоматично; хуки, агенти, `.mcp.json` потребують `/reload-plugins`.
- Сесійний плагін тихо замінює однойменний встановлений — зручно для пісочниці, але варто пам’ятати при діагностиці.
- Альтернатива — додати репозиторій як маркетплейс з локальної папки: плагіни з відносним шляхом вантажаться на місці, зміни видно після `/reload-plugins` без підняття версії. Для клієнтських проєктів так робити не можна (див. «Наслідки», п. 3).
- Також є `CLAUDE_CODE_PLUGIN_DIRS` (v2.1.280+) і `claude plugin init` (створює плагін у `~/.claude/skills/<name>/`, що вантажиться завжди — для нас не підходить).

### 3. Встановлення, оновлення, валідація ✅

**Встановлення:**

- `claude plugin marketplace add <owner/repo | git-URL | локальний шлях>` → `claude plugin install af-core@<ім’я-маркетплейсу>`. Ім’я маркетплейсу береться з `name` у `marketplace.json`, а не з назви репозиторію. Реєструється в `extraKnownMarketplaces` налаштувань користувача.
- Приватний репозиторій: Claude Code запускає `git` неінтерактивно з наявними обліковими даними машини (ssh-agent або credential helper, наприклад `gh auth setup-git`). Власного токена в маркетплейсі немає.

**Оновлення:**

- Фонове автооновлення для сторонніх маркетплейсів **вимкнене за замовчуванням**; вмикається в `/plugin` → Marketplaces або `autoUpdate` в `extraKnownMarketplaces`.
- Вручну: `claude plugin marketplace update <name>` і `claude plugin update <plugin>@<marketplace>`; нова версія діє після `/reload-plugins` або в новій сесії.
- Оновлення визначається порівнянням обчисленої версії: спершу `version` з `plugin.json`, потім із запису, інакше SHA коміту.

**Вбудовані інструменти, яких не було в припущеннях:**

- `claude plugin validate <path> [--strict] [--json]` — маніфести, frontmatter скілів/агентів/команд; коди виходу 0/1/2, придатні для CI. Для директорії з `marketplace.json` перевіряє маркетплейс, але **не відкриває файли плагінів з інших папок** — кожен плагін треба валідувати окремо.
- **Перевірено на практиці** (2026-11-10, Claude Code 2.1.321, Linux, чистий `HOME` без жодних облікових даних і токенів):
  - `validate` **працює без входу в обліковий запис** — у CI достатньо встановити CLI (`npm i -g @anthropic-ai/claude-code`).
  - Ловить: невалідний `homepage`, зламаний YAML у frontmatter скіла (помилка), агента без `description` (попередження → помилка з `--strict`), невідомі поля маніфесту (попередження).
  - **Не ловить:** `"version": "banana"` (semver не перевіряється) і `description` скіла довжиною 1 700 символів (ліміт 1 536 не перевіряється). Обидві перевірки лишаються за нашим `validate`.
  - Валідація маркетплейсу читає `plugin.json` плагінів з відносним шляхом, але скіли й агенти — лише при валідації папки плагіна.
  - Окремо друкуються перевірки для каталогу Anthropic (README, LICENSE, іконка). На код виходу вони не впливають, якщо не передати `--profile directory`. Щоб не мати шуму, у кожному плагіні — `README.md` і `license` у `plugin.json`.
  - Вивід `--json` має стабільні поля `success`, `manifest.errors|warnings`, `contents[]` — придатно для розбору в `validate.ts`.
- `claude plugin tag <path>` — створює git-тег `<name>--v<version>` і перевіряє, що версії в `plugin.json` і маркетплейсі збігаються. Діапазони версій у залежностях між плагінами розв’язуються саме за тегами такого формату.
- `claude plugin eval` — запускає сценарії з `evals/` у плагіні, порівнює з прогоном без плагіна, має грейдер `tool_used: Skill` (чи справді спрацював скіл). Кожен прогін — реальні виклики моделі за рахунок плану.
- Залежності між плагінами: `dependencies` у `plugin.json` з semver-діапазонами.

### 4. Події хуків і формат ✅

**Потрібні нам події існують:**

| Наша потреба | Подія | Деталі |
| --- | --- | --- |
| Старт сесії | `SessionStart` | matcher: `startup`, `resume`, `clear`, `compact`, `fork` |
| Стиснення контексту | `PreCompact` / `PostCompact` | matcher: `manual`, `auto` |
| `/clear` | `SessionEnd` (`clear`) + `SessionStart` (`clear`) | |
| До/після інструмента | `PreToolUse`, `PostToolUse`, `PostToolUseFailure` | matcher — ім’я інструмента |
| Завершення | `Stop`, `SubagentStop`, `SessionEnd` | `StopFailure` — коли хід обірвався помилкою API |

Корисні додатково: `PostToolBatch`, `PermissionRequest`, `PermissionDenied`, `UserPromptSubmit`, `InstructionsLoaded`, `SubagentStart`, `WorktreeCreate`/`WorktreeRemove`, `PreModelSwitch`.

**Вхід (JSON у stdin):** `session_id`, `prompt_id`, `transcript_path`, `cwd`, `permission_mode`, `effort`, `hook_event_name`; у субагенті — `agent_id`, `agent_type`; для інструментів — `tool_name`, `tool_input`, `tool_use_id`.

**Вихід:** код виходу + опційно JSON у stdout (`continue`, `stopReason`, `systemMessage`, `decision`/`reason`, `hookSpecificOutput`).

**Типи хуків:** `command`, `http`, `mcp_tool`, `prompt`, `agent` (експериментальний).

**Тайм-аути за замовчуванням:** 600 с для `command`/`http`/`mcp_tool`, а для `UserPromptSubmit` — 30 с.

**Оболонка залежить від ОС:** у shell-формі (лише `command`) рядок виконується через `sh -c` на Linux і macOS, через Git Bash на Windows, а без Git Bash — через PowerShell. Поле `shell` (`"bash"` чи `"powershell"`) перевизначає вибір. Exec-форма (`command` + `args`) запускає програму напряму, **без жодної оболонки на будь-якій ОС**, і `${CLAUDE_PLUGIN_ROOT}` підставляється в аргументи як звичайний рядок. На Windows exec-форма потребує справжнього `.exe`, а не `.cmd`-шима (`node.exe` підходить). Приклад з документації:

```json
{ "type": "command", "command": "node", "args": ["${CLAUDE_PLUGIN_ROOT}/scripts/format.js", "--fix"] }
```

Поле `timeout` задається в секундах. Хуки `SessionEnd` мають спільний бюджет 1,5 секунди (до 60 с, якщо явно задати більший `timeout`). Детальніше — у розділі «Кросплатформність».

У плагіні хуки лежать у `hooks/hooks.json` під ключем `"hooks"` у тій самій формі, що й у `settings.json`.

### 5. Як SessionStart додає контекст ⚠️

- Простий текст у stdout (exit 0) або `hookSpecificOutput.additionalContext`. Текст загортається в system reminder і ставиться на початок розмови.
- **Ліміт 10 000 символів** на `additionalContext`, `systemMessage` і stdout. Більше — Claude Code зберігає вивід у файл і передає лише шлях і перші 2 000 символів, причому не просить агента читати файл. Критичний контекст має вкладатися в ліміт.
- `SessionStart` додатково приймає `initialUserMessage`, `watchPaths`, `sessionTitle`, `reloadSkills`.

### 6. Як хук блокує дію ✅

- **Exit 2:** stderr — причина. Для `PreToolUse` виклик блокується, і Claude бачить причину; для `UserPromptSubmit` блокується промпт; для `Stop` — агент продовжує роботу. Для `SessionStart`/`SessionEnd` stderr бачить лише користувач.
- **JSON:** `hookSpecificOutput.permissionDecision: "deny"` + `permissionDecisionReason` (також `allow`, `ask`, `defer`; можна змінити вхід через `updatedInput`).
- **Деградація:** будь-який інший ненульовий код, відсутній скрипт, невалідний JSON або тайм-аут **не блокують** дію — у транскрипті з’являється повідомлення про помилку хука. Необроблений виняток у Node завершується кодом 1, тож за замовчуванням це безпечна деградація. Жорстку поведінку вмикає `onFailure: "block"` (v2.1.295+). **Збігається з принципом 6**; лишається правило ніколи не віддавати exit 2 при внутрішній помилці хука.

### 7. Формат скілів ✅

- `skills/<name>/SKILL.md`; frontmatter необов’язковий, але `description` рекомендований.
- Поля: `name`, `description`, `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork` + `agent`, `background`, `hooks`, `paths`, `shell`.
- **Ліміти:** `description` + `when_to_use` обрізаються на **1 536 символах**. Список назв і описів усіх скілів має бюджет **1% контекстного вікна**; при переповненні першими зникають описи найрідше використовуваних скілів. `SKILL.md` — до 500 рядків, деталі — в окремі файли.
- **Прогресивне завантаження:** на старті — лише назва й опис; при виклику — повний `SKILL.md`, який лишається в розмові; допоміжні файли — за потреби, скрипти виконуються, а не вантажаться. Після стиснення повторно додаються перші 5 000 токенів кожного скіла, разом не більше 25 000 — тому найважливіше має бути на початку файлу.
- Плагінні скіли мають префікс: `/af-core:<skill>`.
- **Корисно для «примусу використання скілів»:** поле `hooks` у frontmatter скіла діє від виклику до кінця сесії. Документація радить правила, що мають виконуватися завжди, переносити в хуки, а не в текст скіла.

### 8. Субагенти ⚠️

**Підтвердилось:**

- Файл `agents/<name>.md` з frontmatter. Обов’язкові лише `name` і `description`. У плагіні агент зветься `af-core:<name>`; підпапки додаються до імені.
- **Обмеження інструментів:** `tools` (allowlist) і `disallowedTools` (denylist, застосовується першим). Без `tools` агент успадковує всі інструменти. Специфікатор на кшталт `Bash(git push *)` у `disallowedTools` прибирає весь інструмент; точкові заборони робляться правилами `permissions.deny`.
- **Модель:** `sonnet`, `opus`, `haiku`, `fable`, повний id або `inherit`. Порядок: параметр виклику → frontmatter → `CLAUDE_CODE_SUBAGENT_MODEL` → модель основної розмови. Є також `effort` і `maxTurns`.
- Субагенти вантажать ієрархію `CLAUDE.md`, крім вбудованих Explore/Plan і агентів з `omitClaudeMd: true`. Історії розмови й auto memory вони не отримують; для власної пам’яті є поле `memory`.
- Вкладеність — до 3 рівнів, паралельно — до 20 агентів.

**Відрізняється:** для **плагінних** агентів поля `permissionMode`, `hooks` і `mcpServers` **ігноруються**. Ролі tester/security з плагіна не можуть мати власного режиму дозволів чи власних хуків. Обмеження робимо через `tools`/`disallowedTools`, а хуки — на рівні плагіна з перевіркою `agent_type` у вході хука.

### 9. Правила з масками `paths:` ❌

**Механізм підтвердився:**

- `.claude/rules/**/*.md`; frontmatter `paths:` — єдине поле, яке читає Claude Code (YAML-список або рядок через кому, glob із `**` і `{a,b}`).
- Правило без `paths` вантажиться на старті разом з `.claude/CLAUDE.md`. Правило з `paths` — коли агент читає, пише чи редагує відповідний файл, зокрема через `cat`/`head`.
- Рівень користувача — `~/.claude/rules/`, вантажиться в усіх проєктах; маски там рахуються від основної робочої директорії сесії.
- Симлінк на правила поза проєктом потребує одноразового схвалення, і після нього вантажаться лише правила **без** `paths`.

**Розбіжність з припущенням:** серед компонентів плагіна немає правил і немає `CLAUDE.md`. Принцип «правила з масками `paths:` там, де можливо» реалізовний лише через `.claude/rules/` клієнтського репозиторію (суперечить принципу 2) або через `~/.claude/rules/` (глобально для всіх проєктів і всіх клієнтів — суперечить принципу 8).

**Що плагін може дати замість правил:**

- скіли з полем `paths` (активуються для відповідних файлів, вантажаться на вимогу);
- хук `SessionStart` (≤ 10 000 символів);
- хук `InstructionsLoaded` для спостереження.

**Пов’язані факти:** `CLAUDE.md` — бажано до 200 рядків, імпорти `@path` — до 4 рівнів вкладеності (і не зменшують вартість контексту), HTML-коментарі `<!-- -->` вирізаються перед завантаженням.

### 10. Git worktrees ✅

- `claude --worktree <name>` / `-w` створює `.claude/worktrees/<name>/` на гілці `worktree-<name>`. Є варіант з номером PR (`--worktree "#123"`). Агент може сам зайти у worktree через `EnterWorktree`. У десктоп-застосунку — опція worktree при старті сесії.
- `.worktreeinclude` (синтаксис `.gitignore`) копіює ігноровані файли (`.env` тощо) у новий worktree.
- `worktree.baseRef`: `"fresh"` (від віддаленої гілки за замовчуванням) або `"head"`.
- Прибирання: чистий worktree видаляється автоматично; з незбереженою роботою — питання при виході; для субагентних worktree — періодичне прибирання за `cleanupPeriodDays`.
- Субагенти з `isolation: worktree`.
- Хуки `WorktreeCreate`/`WorktreeRemove` для не-git VCS.
- Worktree поділяє з основним checkout `.git`, плагіни проєктного рівня, дозволи й неіндексовані `.claude/skills|agents|commands`.
- Нюанс для наших хуків: `${CLAUDE_PROJECT_DIR}` лишається на основному checkout, а фактичний шлях worktree — у полі `cwd` вхідного JSON.
- Нюанс для принципу 2: документація радить додати `.claude/worktrees/` у `.gitignore` проєкту.

### 11. Транскрипти сесій ⚠️

**Підтвердилось:**

- Шлях: `~/.claude/projects/<project>/<session-id>.jsonl`, де `<project>` — шлях робочої директорії, у якому всі не алфавітно-цифрові символи замінено на `-`. Назви, довші за 200 символів, обрізаються з хешем.
- Розташування змінює `CLAUDE_CONFIG_DIR`.
- Кожен рядок — JSON-об’єкт повідомлення, виклику інструмента чи метаданих.
- Хуки отримують `transcript_path`.
- Назва папки проєкту залежить від ОС. За правилом заміни символів `D:\Pet Projects\ai-foundations` дає приблизно `D--Pet-Projects-ai-foundations`, а `/home/ivan/ai-foundations` — `-home-ivan-ai-foundations` (це висновок з правила, а не приклад з документації). Аналізатор не має відновлювати шлях з назви папки; справжній шлях береться з полів самих записів.

**Відрізняється:**

- **Формат записів внутрішній і змінюється між версіями** — документація прямо попереджає, що скрипти, які його парсять, можуть зламатися на будь-якому релізі. Поля з токенами, викликами інструментів і помилками **не задокументовані**. Їх доведеться визначити з реальних файлів і тримати парсер толерантним до відсутніх полів, з фікстурами кількох версій.
- **Зберігання — 30 днів за замовчуванням** (`cleanupPeriodDays`). Базова лінія «з уже наявних транскриптів» покриє щонайбільше останній місяць, і щодня частина історії зникає.
- Транскрипти десктоп-застосунку й Cowork мають окремий строк (`desktopSessionCleanupPeriodDays`) і окреме сховище — це окреме відкрите питання.

**Офіційні структуровані інтерфейси:**

- `claude -p --output-format json|stream-json` — usage й вартість прогону;
- `claude -p --resume <id>`;
- `transcript_path` у хуках (наприклад, архівація в `SessionEnd`);
- Agent SDK.

**Схема з реального транскрипту** (2026-11-10). Джерело — транскрипт сесії Cowork у хмарі: 117 записів типу `assistant` і 81 результат інструментів; версія Claude Code змінилася посеред сесії з 2.1.319 на 2.1.321. Документація схему не гарантує, тож це робоча гіпотеза для аналізатора, яку треба підтвердити на транскриптах з Windows-машини.

| Що рахуємо | Де лежить |
| --- | --- |
| Тип запису | `type`: `user`, `assistant`, `system`, `attachment`, `cost-state`, `ai-title`, `last-prompt`, `mode`, `tools-used`, `queue-operation` тощо |
| Сесія, час, версія | `sessionId`, `timestamp`, `version` — у **кожному** записі; `entrypoint` (наприклад, `remote_cowork`), `cwd`, `gitBranch` |
| Токени виклику моделі | `assistant` → `message.usage.input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`, `output_tokens_details.thinking_tokens`; модель — `message.model`; ключ — `message.id` / `requestId` |
| Виклик інструмента | `assistant` → `message.content[]` з `type: "tool_use"`, поля `id`, `name` (вхідні дані — у `input`, їх не читаємо) |
| Результат і помилка інструмента | `user` → `message.content[]` з `type: "tool_result"`, поля `tool_use_id`, `is_error` |
| Рішення про дозвіл (відхилені дії) | `user` → `permissionDecision.decision` (`accept`/…), `.source` (`config`, `user_temporary`, …) |
| Вартість сесії | `cost-state` → `totalCostUSD`, `totalDuration`, `totalLinesAdded/Removed`, `modelUsage.<model>.{inputTokens, outputTokens, cacheReadInputTokens, costUSD, …}`. Це накопичувальні знімки, тож береться **останній** у сесії |
| Робота хуків | `system` з `subtype: "stop_hook_summary"` → `hookCount`, `hookErrors[]`, `hookInfos[].durationMs`, `preventedContinuation` |
| Субагенти | `isSidechain`; транскрипти субагентів лежать окремими файлами |

Пастки, знайдені на реальних даних:

- **Токени дублюються:** одна відповідь моделі записується кількома рядками, по одному на блок вмісту (thinking, tool_use, text), і кожен рядок несе той самий `usage`. Тут 117 записів `assistant` відповідали лише 51 унікальному `message.id`. Сумувати треба по унікальному `message.id`, інакше токени завищаться приблизно вдвічі.
- **Транскрипт містить персональні й клієнтські дані:** повні входи інструментів, вміст файлів і e-mail користувача у вкладеннях. Аналізатор читає лише перелічені поля й ніколи не виводить вміст — тільки агрегати, як і вимагає критерій етапу 1. Те саме стосується фікстур у git — див. «Наслідки», п. 9.

### 12. Вбудована телеметрія (OpenTelemetry) ✅

**Увімкнення:** `CLAUDE_CODE_ENABLE_TELEMETRY=1`. Експортери метрик — `otlp`, `prometheus` (`localhost:9464/metrics`), `console`; подій — `otlp`, `console`. **Файлового експортера немає:** для локального збереження потрібен приймач, наприклад OpenTelemetry Collector.

**Метрики:**

- `claude_code.session.count`;
- `token.usage` (input/output/cacheRead/cacheCreation);
- `cost.usage` з атрибутами `skill.name`, `plugin.name`, `agent.name`, `mcp_server.name`;
- `lines_of_code.count`, `commit.count`, `pull_request.count`;
- `code_edit_tool.decision`, `active_time.total`.

**Події:**

- `user_prompt`, `assistant_response`;
- `api_request` (токени, `cost_usd`, тривалість), `api_error`;
- `tool_decision` (accept/reject, джерело рішення, зокрема `hook`);
- `tool_result` (`success`, `error_type`, тривалість);
- `safety_event` — відмови, промпти дозволів, блокування хуками; v2.1.307+.

Подію `subagent_completed` документація згадує, але її атрибутів ми не бачили.

**Приватність за замовчуванням:** текст промптів, відповідей, команд і шляхів не передається, доки не ввімкнути `OTEL_LOG_*`. Це добре для клієнтських даних.

**Висновок:** OTel покриває майже все, що мав рахувати аналізатор (сесії, токени, вартість з атрибуцією до скілів і плагінів, виклики інструментів, помилки, відхилені дії), і робить це стабільним задокументованим контрактом. Але дані йдуть лише **від моменту ввімкнення** — історичну базову лінію телеметрія не дає. Наближену оцінку раундів правок OTel напряму не дає.

## Довідково: TypeScript у Node без збірки

Перевірено за nodejs.org/api/typescript:

- Зняття типів увімкнене за замовчуванням з **Node 22.18 / 23.6**, стабільне з **24.12 / 25.2**.
- `tsconfig.json` Node не читає.
- Не підтримуються: `enum`, `namespace` з кодом, parameter properties, import aliases, декоратори.
- Розширення `.ts` в імпортах обов’язкові.
- Типи імпортуються лише через `import type`.
- `.ts` у `node_modules` не виконуються.
- Рекомендований `tsconfig` для `tsc --noEmit`: `erasableSyntaxOnly`, `verbatimModuleSyntax`, `rewriteRelativeImportExtensions`, `module: nodenext`.

Хуки плагіна виконуються тим `node`, що знаходиться в `PATH` машини. Якщо `node` немає, це не блокуюча помилка хука, тобто безпечна деградація.

## Кросплатформність: Windows і Linux

Факти з документації, де поведінка залежить від ОС:

| Тема | Windows | Linux |
| --- | --- | --- |
| Оболонка command-хуків у shell-формі | Git Bash, якщо встановлений, інакше PowerShell | `sh -c` |
| Exec-форма хука | без оболонки | без оболонки |
| Exec-форма хука (`args`) | лише справжній `.exe` | будь-який виконуваний файл |
| Зворотний слеш у шляхах компонентів і `source` | працює | шлях **відхиляється** (компонент не вантажиться) |
| Симлінки | потребують Developer Mode або підвищених прав | працюють |
| `command`-джерело плагіна | через `cmd.exe`; режим `link` заборонений | через `sh`; `link` дозволений |
| UNC-шляхи (`\\server\share`) | не вантажаться для правил/`CLAUDE.md`, заборонені для `command`-джерел | — |
| Сховище облікових даних ОС | Windows Credential Manager | Secret Service (libsecret); на машині без графічної сесії може бути відсутнє |
| Де сам Claude Code тримає свій логін | `%USERPROFILE%\.claude\.credentials.json`, захищений правами профілю | `~/.claude/.credentials.json` з правами `0600` |

Що з цього випливає для нас:

- **Шляхи** в маніфестах і `hooks.json` — лише з прямими слешами. У коді — тільки `node:path` і `os.homedir()`, без зашитих `\` чи `/` і без `~` у рядках.
- **Хуки викликаємо в exec-формі** (`node` + шлях до `.ts` в `args`), щоб не залежати від Git Bash, PowerShell чи `sh` і їхніх правил лапок. Синтаксис звірено — див. пункт 4.
- **Жодних bash-скриптів як логіки.** Тонкі обгортки, якщо знадобляться, мають бути й для PowerShell, або їх не має бути взагалі.
- **Регістр імен файлів:** Linux розрізняє `Context.md` і `context.md`, Windows — ні. Імена й посилання — завжди в нижньому регістрі (kebab-case уже це забезпечує).
- **Кінці рядків:** `.gitattributes` з `* text=auto eol=lf`, щоб фікстури хуків і порівняння в `sync --check` не ламалися через CRLF на Windows.
- **Симлінки не використовуємо** взагалі — це ще один аргумент на користь копій + `sync --check`.
- **Секрети:** абстракція над сховищем ключів з двома реалізаціями; без доступного сховища — запасний файл на клієнта з правами лише для власника: `~/.config/ai-foundation/secrets/<клієнт>.env` або `%APPDATA%\ai-foundation\secrets\<клієнт>.env`, поза `~/ai-foundation-data/` (ту теку захищає бекап) і з виключенням з бекапу (див. «Відкриті питання», п. 7).

## Наслідки й ухвалені зміни

1. **Доставка на машини — закрити як «Прийняте»:** git-маркетплейс + `claude plugin marketplace add` / `install`; автооновлення вмикаємо вручну на своїх машинах; реліз = підняття `version` у `plugin.json` (лише там, не в маркетплейсі) + `claude plugin tag`.
2. **Мінімальна версія Node:** 22.18+ (змінено при затвердженні: на основній машині Node 22.22.2, а з 22.18 зняття типів увімкнене за замовчуванням і без попереджень). CI перевіряє Node 22 і 24. Підтримка Node 22 закінчується у квітні 2027 — до того мінімум піднімаємо до 24. `tsconfig` з `erasableSyntaxOnly` + `verbatimModuleSyntax`, щоб `tsc --noEmit` ловив несумісний синтаксис.
3. **Розробка:** `claude --plugin-dir ./plugins` у пісочниці. Клієнтські машини додають маркетплейс з git, а **не** з локальної папки: локальна папка вантажить робочу копію на місці й ігнорує версії.
4. **`npm run validate`** викликає `claude plugin validate --strict` для `.` і для кожного `plugins/af-*` з `--json` і розбирає результат. Без автентифікації `validate` працює (перевірено), тож у CI достатньо встановити CLI. Semver і довжину опису скіла перевіряє наш код.
   - **Дві різні версії — дві різні ролі.** Вимога до машин, де працюють плагіни, — нижня межа: **≥ 2.1.321**, бо локальний Claude Code оновлюється сам і завжди буде новішим. CI — це тестовий стенд, і він має перевіряти **конкретну** версію: «≥» при встановленні з npm означає «найновішу на момент прогону», тобто той самий плаваючий CI. Закріплена версія CI дорівнює нижній межі, тож ми гарантовано перевіряємо найстаріше, що підтримуємо.
   - **Рання сигналізація:** другий, не блокуючий job CI на `@latest` (раз на тиждень або на кожен push). Його падіння не ламає збірку, а означає «час свідомо піднімати версію».
   - **Версія CLI в CI закріплена точно:** `npm i -g @anthropic-ai/claude-code@2.1.321`, без `latest` і без діапазонів. Формати й правила валідатора змінюються між релізами, і плаваюча версія може зламати CI без жодних змін у нашому коді. Версію тримаємо в одному місці (наприклад, у `package.json` → `config.claudeCodeVersion`), щоб CI і документація брали її звідти.
   - **Підняття версії — свідомий крок** окремим комітом: оновити закріплену версію, прогнати `validate` і тести аналізатора, переглянути changelog Claude Code на зміни в маніфестах, хуках і форматі транскриптів, записати в `CHANGELOG.md`. Разом із нею піднімається й нижня межа для машин.
   - Локально Claude Code оновлюється сам, тож машина розробника може бути новішою за CI. Розбіжність допустима; якщо локальний `validate` дає інший результат, ніж CI, це сигнал підняти закріплену версію.
5. **Хуки:** у кожного хука явний короткий `timeout`; exit 2 лише для свідомого блокування; внутрішня помилка → exit 0 + повідомлення про деградацію. Шлях проєкту беремо з `cwd`, а не з `${CLAUDE_PROJECT_DIR}` (через worktrees). Тести на фікстурах покривають і Git Bash, і PowerShell-запуск на Windows.
6. **Контекст на старті** вміщується в 10 000 символів; шаблон `context.md` проєктуємо під цей ліміт.
7. **Правила `paths:`** — переглянути архітектурне правило в `CLAUDE.md`. Пропозиція: «постійний контекст — бюджет: умовні інструкції — скіли з `paths`; обов’язкові правила — хуки». Варіанти з `.claude/rules/` клієнтського репо чи `~/.claude/rules/` — лише окремим рішенням.
8. **Ролі** (tester, security) як плагінні агенти: обмеження через `tools`/`disallowedTools`; хуки й MCP — на рівні плагіна з фільтром за `agent_type`.
9. **Аналізатор історії:** читати `~/.claude/projects/**/*.jsonl` толерантно до формату, за схемою з пункту 11. Токени сумувати по унікальному `message.id`. Фікстури позначати полем `version` із самих записів.
   - **Фікстури лише синтетичні або очищені.** Фікстури потрапляють у git, тож реальний транскрипт із клієнтського проєкту там неприпустимий, навіть один і навіть частково. Фікстури будуються з реальних файлів лише як зразок структури: усі значення замінюються на вигадані (`cwd: "/fixtures/project-a"`, `sessionId` згенерований, `message.content` з текстом-заглушкою), а `tool_use.input`, вміст `tool_result` і вкладення (`attachment`) — порожні або з заглушкою.
   - **`validate` перевіряє фікстури** (`plugins/*/tests/fixtures/**`) і падає, якщо знаходить:
     - e-mail-адреси;
     - абсолютні шляхи поза дозволеним префіксом `/fixtures/` — Windows (`X:\`, `\\server\`), Linux і macOS (`/home/`, `/Users/`, `/root/`), `~/ai-foundation-data`;
     - непорожні `tool_use.input`, вміст `tool_result` чи вкладень, крім узгодженої заглушки;
     - рядки, схожі на токени чи ключі (та сама перевірка, що й «Секрети» для всього репо).
   - Перевірка працює як allowlist, а не лише як пошук заборонених шаблонів: дозволені тільки поля зі схеми пункту 11 і значення-заглушки; усе інше — помилка. Так нове поле в майбутньому форматі транскрипту не проскочить у git непоміченим.
   - **Уже зараз підняти `cleanupPeriodDays`** (наприклад, до 365; мінімум — 1, а вимкнути очищення не можна), щоб історія не зникала до появи аналізатора. Після базової лінії перейти на OTel.
10. **Worktrees у клієнтських репо:** `.claude/worktrees/` додавати не в `.gitignore` (це змінює репозиторій), а в `.git/info/exclude` (локально, не комітиться).
11. **CI з першого етапу на двох ОС:** матриця GitHub Actions `ubuntu-latest` + `windows-latest` для `npm run validate`. Це змінює рядок у `docs/tech-start.md` («CI — GitHub Actions на Linux; macOS додаємо пізніше»): Windows додається одразу, macOS — як і раніше, пізніше. Критерій готовності етапу 1 доповнити пунктом «перевірки проходять на Windows і Linux, плагіни встановлюються на обох».
12. **Ручна перевірка хуків** у пісочниці — на обох ОС (на Linux достатньо WSL або VM), бо оболонки, які запускають хуки, різні.

| 1 | Версія Claude Code: встановлена й мінімальна | ◐ | Мінімум — **≥ 2.1.321**. Технічно потрібні фічі з’явилися раніше (папка плагінів у `--plugin-dir` — 2.1.281, валідація маркетплейсу разом із плагінами — 2.1.289), але перевірено все лише на 2.1.321, тож мінімум дорівнює версії, на якій ми тестуємо. Мінімум піднімається разом із закріпленою версією CI. На основній Windows-машині встановлено 2.1.321 (2026-11-10). Лишилось: перевірити Linux-машину, коли вона з’явиться в роботі |
| 2 | `claude plugin validate` у CI без входу | ✅ | Працює без жодних облікових даних — див. пункт 3 |

| 4 | Схема полів транскрипту | ✅ | Визначено з реального файлу (п. 11) і підтверджено інвентаризацією на Windows-машині 2026-11-20: 63 файли, 60 959 записів, 0 невалідних, 27 версій Claude Code (2.1.260–2.1.329). Поля токенів, інструментів, помилок і дозволів збігаються; додатково є типи `api-request`, `api-request-blob` (копія розмови — у метриках не рахувати), `api-request-shape`, `permission-mode`, `session-owner`, `file-history-delta`, `custom-title`, `agent-name`. Локальних транскриптів Cowork немає: хмарні сесії пишуть транскрипт у хмарному середовищі. Історія на Windows сягає 10.09.2026 — довше за 30 днів |
